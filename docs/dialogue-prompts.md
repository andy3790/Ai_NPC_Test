# NPC 대화 프롬프트 변경과 검증

대화의 자연스러움은 문장 길이·반말·거절 횟수로 판정하지 않는다. **상대의 말에 맞게 반응하고, 관계에 맞는 말투를 유지하며, 답을 기다릴 자리를 남기는지** 원문으로 비교한다. 긴 설명을 청한 상황에는 충분히 설명해야 하고, 친절한 인물이 무조건 까칠해지거나 질문에 침묵하는 것은 개선이 아니다.

## 버전과 이유

| 버전 | 변경 이유 | 변경 범위 |
|---|---|---|
| `npc-dialogue/1` | 변경 전 대조군 보존 | 이 작업 시작 때의 로컬 `npc-lab/6` 공통 연기 문단을 그대로 동결. 예전 Git HEAD의 `/5` 전체 프롬프트와 같다는 뜻은 아님 |
| `npc-dialogue/2` | 답변 뒤 해명·대안·조건·부탁을 묶는 상담형 발화 감소 | 상대 답을 기다릴 자리, 각자의 관심사, 아는 정보를 말할 이유, 관계에 맞는 존댓말과 필요한 긴 설명을 명시 |
| `npc-dialogue/3` | v2의 친구 연습 경험 단정 보완 | 새 공유 과거와 상대의 알려지지 않은 경위를 즉흥적으로 보태지 않도록 경계 복원. 현재 기본값 |
| `npc-lab/7` | 선택한 지침과 실제 사용된 지침의 추적 | 공통 연기 문단을 버전 모듈로 분리하고 실행별 선택을 고정. 세계·공간·행동 결과 권한은 유지 |

정확한 문구와 이유는 [dialogue-policies.ts](../src/core/dialogue-policies.ts), 기본 버전은 [dialogue-policy.ts](../src/shared/dialogue-policy.ts)에 있다. 이미 기록된 버전의 본문을 수정하지 말고 `/3`, `/4`처럼 추가한다. 회귀 테스트의 고정 SHA-256은 기존 문구를 몰래 바꾸는 것을 감지한다. 새 버전마다 문제 출력, 가설, 비교 조건, 실제 결과, 부작용과 채택 여부를 이 문서와 검토 보고서에 추가한다.

실험 편집기의 **대화 반응 지침**에서 v1/v2/v3를 고를 수 있다. JSON에서는 조건별 `dialoguePromptVersion`을 지정한다.

```json
{"id":"candidate","label":"반응 지침 v3","dialoguePromptVersion":"npc-dialogue/3","stopOnSilence":true}
```

생략하면 새 실행 생성 시 현재 기본값을 `run.variant`에 고정한다. 원본 spec은 보존하므로 실제 선택은 실행 스냅샷의 variant에서 확인한다. 대기 중에 기본값을 바꾸어도 생성된 실행은 따라 바뀌지 않는다. 이미 생성된 NPC 세션의 지침은 재개 시 다시 작성하지 않는다. 버전이 없던 이전 실행에서 아직 생성되지 않은 세션은 대조군 `/1`로 만든다. 이 경우 정확한 과거 `/5` 재현이라고 주장하지 않는다.

호출의 `metadata.promptVersion`은 실행 생성 때의 버전, `runtimePromptVersion`은 현재 실행 코드의 버전이다. `dialoguePromptVersion`과 `instructionsSha256`으로 선택한 정책과 실제 세션 지침을 확인한다. 과거에 없던 버전은 `null`로 남기며 현재 버전으로 소급 표기하지 않는다. 원본 세션 지침과 호출 입력은 기존 내보내기에 보존된다.

캐릭터 프로필의 지침도 출력에 영향을 준다. 예를 들어 ‘상대의 말을 요약한 뒤 의견을 말한다’, ‘합의할 선택지를 정리한다’는 프로필은 상담형 발화를 유도한다. 인물 고유 특성이면 보존하고, 모든 인물에 복사한 공통 문구라면 별도 프로필 버전으로 비교한다. 공통 정책과 프로필을 동시에 바꾼 결과를 공통 정책만의 효과로 주장하지 않는다.

## 고정 입력 비교

[cases.json](../evals/dialogue/cases.json)은 8개 개발 사례와 4개 보류 사례를 분리한다. 쉬운 부탁, 거절, 취향, 실망, 신난 긴 설명, 고객 응대, 모르는 정보, 자기 시간 보호, 사과, 직장 존댓말, 비공개 정보, 못 들은 질문을 포함한다. 참고 판정 기준과 타인의 비공개 프로필은 NPC 입력에 넣지 않는다. 보류 사례는 후보 문구를 동결한 뒤 실행한다.

```powershell
# 호출 없는 실행 계획
npm run dialogue:eval

# 동일 모델, 새 세션, 정책마다 사례당 3회
npm run dialogue:eval -- --live --split development --max-calls 48 --max-usd 2
npm run dialogue:eval -- --live --split holdout --max-calls 24 --max-usd 2

# 로그인된 Codex 실행 경로. 모델은 실제 설치 환경에서 지원해야 함
npm run dialogue:eval -- --adapter codex --model gpt-6-sol --live --split development --max-calls 48 --max-usd 2

# 이전 후보를 그대로 재실행
npm run dialogue:eval -- --candidate npc-dialogue/2

# 두 장면, 정책별 최대 18차례, 새 NPC 세션으로 이어지는 대화 검토
node --import tsx scripts/dialogue-soak.ts --adapter codex --model gpt-6-sol --live --max-usd 3
```

명시적으로 `--live`를 넣어야 모델을 호출한다. 실패·불확실 응답·사용량 누락·예산 도달 시 중단하고 자동 재요청하지 않는다. `max-usd`는 저장된 사용량과 로컬 가격표에 따른 다음 요청 차단선이며 마지막 한 요청은 초과할 수 있다. Codex 비용은 API 단가 환산치일 뿐 실제 구독 청구 금액이 아니다. 공급자·모델이 다른 표본은 별도 결과로 취급한다.

`.cache/dialogue-eval/`에 고정된 사례, 정책, 입력 전체, 응답 원문, 공급자 이벤트, 사용량, 입력 해시, A/B 매핑과 `review.md`를 남긴다. A/B의 순서와 먼저 호출하는 정책을 교차 배치한다. 검토 파일만 보면 정책 이름이 없지만 작성자가 매핑을 아는 검토는 **비독립 에이전트 검토**로 표시한다. 사람이 평가하지 않았다면 사람 평가라고 쓰지 않는다. 실패는 삭제하거나 완료된 표본 수에 포함하지 않는다.

## 채택 기준과 다음 실험

각 비교에 `A/B/tie/neither`와 근거 인용을 적는다. ① 문맥에 맞는 대꾸 ② 과잉 해설·선제 대안 ③ 고유 목소리·존댓말 ④ 필요한 정보 ⑤ 지식·행동 권한을 따로 본다. 짧은 응답을 자동 우승시키지 않는다. 설정 위반이나 필요한 답의 누락은 자연스러움이 좋아도 별도로 남긴다.

단일 차례 비교는 긴 대화의 리듬을 보장하지 않는다. 기본 정책을 바꾸기 전 새 세션의 여러 차례 대화도 읽는다. 반복 상담, 질문 연쇄, 행동만 반복하는 침묵, 즉각 화해, 같은 말투로 수렴하는지 확인한다. 새 문제가 생기면 사례를 추가하고 데이터셋 버전을 올린다. 고정 입력에 맞춘 문장 외우기나 출력 후 강제 절단은 사용하지 않는다.

## 침묵과 장면 종료

단일 공간 NPC는 `speech`와 `action`을 둘 다 빈 문자열로 내어 차례를 넘길 수 있다. 이는 검증 실패가 아니다. 원본 선택·호출·사용량은 보존하지만 빈 내용으로 다른 NPC의 수신 호출을 만들지 않는다. 화면에는 대사를 지어 넣는 대신 ‘발언·행동 없이 차례를 넘김’이라는 기록 표시를 한다. 기존 `speechCount`는 말이 있는 문장 수가 아니라 NPC 선택 차례 수이므로 실제 발언 수는 원문에서 따로 세어야 한다.

`stopOnSilence:true`는 **환경 꺼짐**에서만 적용한다. 마지막 실제 발언·행동·상황 뒤 모든 NPC가 한 번 이상 연속해서 조용히 차례를 넘겼고 예정된 미적용 사건이 없으면 `conversation_idle`로 끝난다. 한 인물의 침묵, 몸짓이 있는 차례, 규칙·AI 세계·분산 공간은 이 종료 조건을 적용하지 않는다. 기본값은 꺼짐이며 기존 고정 발화 수 실험은 유지한다. 새 일상 예제와 대화 검토 도구만 이 옵션을 켠다. 분산 공간의 선택/활동 계약은 이번에 변경하지 않았다.

평가 절차는 [OpenAI의 평가 지침](https://developers.openai.com/api/docs/guides/evaluation-best-practices)과 [코드로 관리하는 프롬프트 지침](https://developers.openai.com/api/docs/guides/prompting)을 참고했다. 이 저장소의 통과 여부는 자체 실행 증거이며 공식 지침 자체가 품질을 보증하지 않는다.
