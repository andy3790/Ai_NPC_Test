# 관측기지에서 첫 사건 다음으로 넘어가는가

같은 관측기지 입력으로 수정 전, 1차 수정, 최종 수정의 대사와 행동, 세계 판정을 저장했다. 대조군은 `2ee3d3a`의 엔진에서 82차례 뒤 이동 판정에 멈췄다. 같은 실패 지점에서 얻은 응답 6개를 모두 보존해 로컬에서 이동 규칙을 검증했다. [차례별 원문 비교](comparison.md) · [구조화 원문](transcript.jsonl) · [사용량과 버전](usage.json)

## 기존 장기 기록

- 관측기지 `station-rest-256`의 첫 행동은 윤의 “소매를 걷고 환풍기 쪽으로 다가가 진동음과 고정 상태를 살핀다.”였다. 250차례에도 도하가 “나사 하나가 그렇게 티를 내네. 진동 잦아들었으면 오늘은 그만 괴롭혀도 되겠다.”라고 했다. 세계 시간은 609.97초였다. [이전 관측기지 원문](../topic-memory-2026-11-08/transcript.jsonl)
- ‘닫히는 문’의 `choice-door-long`에서는 24초에 문이 닫혔지만 125번째 선택이 “손 넣어 확인할게요. 판은 그대로 받쳐 주세요.”였다. `release-call`에서는 148번째 발언에서 내일 정오에 사본을 주겠다고 했고, 160차례 시계는 479초였다. 말로 한 약속이 세계의 예정 사건으로 등록됐다는 보장은 없었다. [이전 두 장면의 원문](../luna-scenes-2026-11-08/transcript.jsonl)

## 실행 조건

세 실행 모두 같은 `examples/spatial-world.json`에서 4명, 3개 장소, `spatial-events`, 화자 순환, 차례별 묶음 수신을 사용했다. NPC 및 상황 생성은 Luna low, 시간 계획과 세계 판정은 Luna medium이다. 선택 상한은 각각 128회다. 실제 생성·판정만 실행했고, 평가는 기록된 원문을 읽어 진행했다. 사용량은 API 응답의 토큰과 저장소 단가를 사용해 형식 재시도까지 합산했다. [사용량·설정 지문](usage.json)

## 대화와 세계 판정

| 장면 | 실제 원문과 판독 |
|---|---|
| 기존판에서 끝냈던 환풍기 | 60차례 윤 “요즘은 무난해요. 오늘 환풍기 진동 점검까지 끝내서 이제야 한숨 돌리네요. 미루 씨는요?” 82차례 같은 인물 “그럼 저는 작업실로 돌아가 환풍기 진동을 마저 확인할게요.” 사이에 무전 잡음은 있었지만 환풍기가 다시 나빠졌다는 관찰은 없었다. |
| 최종 API에서 물컵이 일으킨 일 | 관찰 순번 39 “물컵이 윤의 손에 들려 있다.” 60초에 세계가 이 관찰을 원인으로 물방울이 흐르는 사건을 채택했다. 29차례 세린이 탁자를 닦은 뒤 30차례 도하 “탁자 쪽은 닦였네. 바닥 물방울은 미끄러우니까 이것도 닦아둘게.” 세계가 바닥 물방울이 사라졌다고 판정했고, 32차례 윤 “바닥까지 닦아주셔서 고마워요. 이번엔 컵을 탁자 안쪽에 두고 마실게요.” 이후 세계 기록에서도 컵은 탁자 안쪽에 놓였다. |
| 긴 휴식 뒤 | 83차례 윤 “저는 조금 더 쉬고 싶어요. 귀가 아직 좀 피곤하네요.” 휴식 후 9분 4.7초에 도하가 “슬슬 일어날까 싶은데, 작업실이나 관제실에 손 필요한 사람 있어?”라고 먼저 일어났다. 다른 세 사람은 더 쉬겠다고 답했다. 128차례에는 미루가 실제로 관제실로 돌아가 장비를 살폈다. |

윤은 자기가 느끼는 불편을 짧은 존댓말로 말하고 도하는 눈에 보이는 일을 반말로 제안하는 차이를 보였다. 미루는 101차례에 “윤, 귀는 좀 괜찮아졌어?”라고 했다. 그 직전 99차례 세린이 이미 귀가 괜찮아졌는지 물었고, 102차례에는 세린이 또 같은 질문을 했다. 물컵도 윤이 들고 있는데 23차례 미루는 탁자에 놓인 컵 손잡이를 만지려 했다. 81차례에 환풍기 점검을 끝냈다고 한 도하는 100차례에 다시 점검하러 갔다.

이 한 장면에서는 설비 점검에서 휴식·물 닦기·무전 응답으로 행동이 달라졌고, 빈 시간을 생략한 뒤 누가 다시 움직였는지 읽을 수 있었다. 새 문제가 약한 후반에는 안부 확인과 정리가 돌아왔다. 다른 장르나 이름만 있는 인물에서도 대사의 자연스러움이 같은 수준일지는 이번 유료 대조로 판정할 수 없다. [전체 원문](comparison.md)

## 엔진 검증

- 기존판 82차례에서 윤은 휴게실에서 작업실로 가겠다고 하고 소매를 걷었다. 시간 계획에서 윤은 출발하지 않았고 세린은 아직 이동 중이었다. 기존 모델 출력 형식은 잘못된 도착을 여섯 번 모두 허용했고, 서버의 상태 검사에서 모두 거절했다. 최종 출력 형식으로 같은 여섯 응답을 재생하면 여섯 번 모두 도착 선택 자체가 허용되지 않는다.
- 1차 수정본의 128개 NPC 입력에서 당시 개인 기억과 시각을 복원했다. 2분 이상 쉬려다 조기에 차례가 온 27건 중 2건은 세계가 반응을 요구한 경우였다. 최종 규칙은 같은 이력에서 조기 호출 8건을 더 미뤘다. 예를 들어 75번째 선택에서 5분을 고른 윤은 8.1초 뒤 의자 밑에 컵이 없다는 결과에 다시 불렸다. 재생은 당시 이력을 고정하고 각 차례에서 누가 선택 대상인지 판정한 것이다.
- 인물 이름만 두 개, “작은 방.”, “두 사람이 있다.”를 넣은 테스트에서 두 수신 방식 모두 쉬기로 한 뒤 120초에 대화가 이어졌다. 기다리는 동안 40초에 예정된 답장이 오면 먼저 사건을 확정했고, 응답 수신 확인이 유실된 뒤에도 한 번만 반영했다. 8시간 뒤 자료 수신을 예약한 경우에는 둘이 계속 쉴 때 32차례 안에 정확히 8시간에 자료가 도착했다. 분산 공간은 50초 통로 폐쇄와 60초의 현장 신호 사이를 건너뛰지 않았다. 이 최소 입력 사례들은 모의 모델로 서버의 작동을 검증했다. [회귀 테스트](../../../tests/scene-flow.test.ts)
- 최종 유료 실행은 `scene-flow/2`, 새 실행의 서버 기본값은 `scene-flow/3`이다. /3의 2분 경계와 먼 기한 처리는 오프라인으로 검증했다. /2 원본에 기록된 128개의 NPC 입력을 모두 재현했고, 같은 기록에서 91번째 조기 호출 한 건은 /3에서 더 기다리게 된다. 관측기지에서 먼 기한 보정이 바꾼 대기는 0건이었다. 그 뒤의 대사는 원래 API 출력이다. [버전별 변경 이유](../../dialogue-prompts.md)
