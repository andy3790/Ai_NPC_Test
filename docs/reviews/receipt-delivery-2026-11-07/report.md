# 매 발화 전달 수신 조사·최적화 · 2026-11-07

같은 NPC에게 **발화와 직후의 환경 확정 결과를 각각 전달**하고 있었다. 최근 실제 실행 두 개에서 동일한 `발화 ID + 수신 NPC`의 중복 호출은 없었다. 다만 같은 작업에 속한 두 관찰을 각각 확인하므로 호출이 불필요하게 늘었다. 두 내용을 순서대로 한 번에 전달하도록 수정했다.

## 확인한 실제 기록

조사한 실행은 `f2186ef7-d12b-46e6-8ac0-01949846ab03`과 `2117fc06-5da4-4c9b-9067-e30e5a4e4ca7`이다. 당시의 실제 [호출 원본](../harbor-stability-2026-11-07/app-final/each/calls.jsonl)과 [대화 원문](../harbor-stability-2026-11-07/app-final/each/transcript.md)을 현재 앱의 데이터와 대조했다. 두 실행 모두 실패·재시도로 인해 같은 대상에게 재전송한 사례는 없었다.

최근 실행의 첫 차례는 다음과 같다.

1. 윤이 “기름부터 볼게요. 낮에는 한 통이었는데, 불을 켜기 전에 직접 확인해야겠어요.”라고 말하고 기름통을 살핀다. 도하·미루에게 각각 수신 확인을 호출했다.
2. 규칙 엔진이 남은 기름 확인 결과를 확정했다. 윤·도하·미루에게 각각 수신 확인을 다시 호출했다.

따라서 이 한 차례에 수신 **5회**가 발생했다. 윤에게도 결과를 전달하는 이유는 본인이 행동을 시도한 것과 엔진이 성공을 확정한 것이 다르기 때문이다. 윤의 발화 자체를 윤에게 재입력하지는 않았다. 다른 사람의 동의나 물리 결과도 같은 이유로 확정 기록을 유지한다.

## 바뀐 처리

- 발화와 바로 다음 규칙 결과가 한 트랜잭션에서 확정됐고, 결과가 해당 발화 ID를 가리키는 경우만 합친다.
- 도하·미루는 `[윤의 발화, 확정 결과]`를 순서대로 받고 `received:true`를 한 번 반환한다. 윤은 확정 결과만 받는다. 같은 예의 수신 호출은 **5회 → 3회**다.
- 원본별 receipt는 유지한다. 같은 호출에 receipt 두 개가 연결되며, 한 묶음의 완료 상태는 원자적으로 저장한다.
- 다음 발화는 모든 대상의 필요한 수신이 끝난 후 시작한다. 다른 발화, 수동·예약 사건, AI 세계의 결과는 이번 최적화로 합치지 않는다. 모아 전달 방식은 그대로다.
- 이미 시도한 호출의 구성은 유지한다. 구버전의 단일 수신, 실패한 통합 수신, 성공했지만 저장이 실패한 호출 모두 기존 요청 구성과 operationKey로 복구한다. 미확정 호출을 새 묶음으로 바꿔 재전송하지 않는다.
- 매번 전체 과거 기록마다 수신 테이블을 다시 조회하던 부분도 미전달 기록을 한 번 분류해 처리하도록 바꿨다. 이 로컬 처리의 시간 개선 폭은 별도로 측정하지 않았다.

수신 문구는 `npc-receive/1`을 보존하고 복수 관찰용 `npc-receive/2`를 추가했다. 발화와 엔진 결과를 별개 기록으로 구별하면서 순서대로 기억하도록 명시한다. 조립 정책은 `receive-delivery/2`다. 호출 metadata에 실제 버전을 기록하고 새 문구 해시를 동결했다. NPC 연기 지침 v5와 인물 프로필 v4는 바꾸지 않았다.

## 같은 대화의 전후 재생

저장된 NPC·진행자 출력을 그대로 재생하고 각 인물에게 들어가는 관찰을 펼쳐 비교했다. 원본 ID를 순번으로 정규화한 뒤 **내용과 순서가 모두 일치**했고, 같은 관찰의 누락·중복도 없었다. 품질 평가 응답은 모의 응답이므로 대화 자연스러움 평가로 해석하지 않는다.

| 기존 대화 | 수신 호출 | 전체 호출 | 수신 기록 행 | 결과 |
|---|---:|---:|---:|---|
| 진행자 방식, 9차례 | 42 → **26** | 61 → **45** | 42 유지 | 모든 목표 완료 |
| 순번 방식, 12차례 | 48 → **32** | 62 → **46** | 48 유지 | 모든 목표 완료 |

각 실행에서 16회가 줄었다. 최근 9차례 사례의 수신 호출은 약 **38.1%**, 전체 호출은 약 **26.2%** 감소했다. 이는 결정론적 엔진 재생의 호출 수 검증이다. 실제 API 토큰·지연·청구 비용의 감소율이 아니다. [재생 결과와 인물별 관찰 해시](replay.json)를 보존했다.

```powershell
npm run receipts:replay
npm run smoke:receipts
```

## 실제 API 검증과 화면

현재 기본 프로필 v4를 사용해 매 발화 전달을 한 번 새로 실행했다. `gpt-6.1-sol/low` NPC, `gpt-6-luna/low` 진행자·평가자, 기존 규칙, 최대 18차례, 호출 동시성 1, 자동 재시도 없이 진행했다.

- 9차례, **전체 45회·수신 26회**, 수신 기록 42개, 통합 수신 16회.
- 합의·점등·기록 목표 완료, 미전달 0, 같은 관찰·수신자 조합의 중복 0.
- 실제 요청 본문·모델·추론 강도·세션 지침·응답 ID 연결과 관찰 순서, 다음 발화 전 수신 완료를 확인했다.
- 로컬 가격표 추정 비용은 **$0.120350775**였다. 이전 대화는 프로필 v2였고 캐시 상태도 다르므로 비용·속도 전후 비교로 쓰지 않는다. 호출 수 감소가 같은 비율의 비용 감소를 보증하지 않는다.

[실제 대화](live/transcript.md), [요청 본문](live/api-requests.jsonl), [수신 연결](live/receipts.jsonl), [호출·사용량](live/calls.jsonl), [설정](live/config.json)을 함께 남겼다. API 키와 헤더는 포함하지 않는다.

수신 상태 화면에는 ‘윤 발화 #1’과 ‘발화 #1 환경 결과’를 구분하고 같은 호출인 행에 ‘함께 수신 (#1 · #2)’를 표시한다. 호출 화면도 ‘관찰 2건 함께 수신’으로 표시한다. 브라우저에서 원본 5개·수신 호출 3회, 실제 두 관찰 입력, 모바일 표, 페이지 오류 없음을 확인했다.

내보내기에는 전체 연결을 `receiveInvocationIds`·`sharedReceiveCalls`·`invocation-links.csv`에 남긴다. 기존 `receiveTokens`·`receiveCalls`는 묶음의 첫 원본에만 계상하므로 토큰·비용을 두 번 더하지 않는다. 전체 합계는 고유 호출 ID가 기준이다.

## 회귀 검사와 적용

전체 **197개 테스트**, 타입 검사, 빌드, 브라우저 검증을 통과했다. 테스트에는 인물별 관찰 내용·순서·중복, 수신 실패, 완료 저장 중단, 구버전 단일 호출 복원, 미확정 호출 차단, 일반 사건 분리, 내보내기 연결을 포함했다. [검증 결과](validation.json)와 [파일 해시](manifest.json)에 실행 증거를 기록했다.

새 수신 처리와 화면은 로컬 서버에 반영했다. 기존 114개 실행·일시정지 6개·저장 설정을 유지하고 실제 검증 실행 1개를 추가했다. 기존 완료 실행의 호출 수·비용·수신 기록은 당시 값으로 보존하며, 과거 42회가 화면에서 26회로 바뀌지는 않는다. 새 실행과 이후 아직 시도하지 않은 전달부터 새 처리를 사용한다. 기존에 전송을 시도한 요청은 원래 구성을 유지한다.
